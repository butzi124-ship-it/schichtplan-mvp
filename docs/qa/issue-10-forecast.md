## Calculation and interpretation

`js/production-forecast.js` is pure, bounded and deterministic for a given input/as_of. Explicit s/min/h units use Temporal 0.5.1 (pinned) for actual elapsed time, local calendars and an explicit DST ambiguity policy. Missing Soll or actual values remain unknown. Actual processing time is reconciled against completed quantities as variance; subtracting all historical processing again would credit finished pieces twice. Only explicitly recorded progress on the current unfinished piece reduces its remaining Te. Setup progress reduces Tr; an overrun requires confirmed remaining setup or setup completion. Unresolved quantities and scrap without a confirmed replacement disposition prevent a reliable finish.

The scheduler reserves machine capacity units and qualified people globally, including across machines and independent BAs. Setup always needs personnel. Processing may be unmanned only with explicit machine, operation AND calendar permission. It respects breaks, holidays, blocked intervals, local dates, paused BAs, documented OP waiting bounds and predecessors. Stable running/priority/ID ordering makes it reproducible; this is a conservative priority scheduler, **not a global optimum or a probability model**. Unknown competing workload contaminates its connected machine/personnel/dependency component rather than consuming zero hours. Insufficient known capacity within the reviewed horizon is red; missing coverage is unknown. Long-running, unbounded reservations consume the reviewed horizon, without inventing a restart ETA.

Green: finish before due and available working-time buffer >= `green_buffer_seconds`. Orange: finish before due with less buffer; `orange_buffer_seconds` marks the especially critical reserve. Red: finish after due or known capacity exhausted. Unknown/stale never green. Both thresholds must be configured, orange <= green; no default thresholds are invented. BA due dates are inclusive local calendar dates (next local midnight is the calculation boundary). UI shows OP/BA finish, remaining hours, joint capacity, buffer, bottleneck, timestamp, legend and missing/stale information. No invented percentages.

Existing stations, employee counters, quantities and checklists are never written by this feature.

## SQL/security and trusted runtime

`supabase/review/issue-10-production-forecast.sql` is unregistered review SQL. It requires reviewed #7, #8 and #9 files first. No Supabase CLI was run (the earlier automatic approval review rejected its telemetry-capable invocation); registration and advisors require a separately approved isolated workflow.

All new tables have RLS enabled and no authenticated/anon table privileges or permissive policies. User RPCs recheck existing department scopes; machine-only grants can read only their existing OP scope and cannot calculate/report. No metadata roles or client-asserted actor IDs are trusted. Calculation input is authorized by the caller JWT. Only the server/service role may publish calculated results or process the queue. The server verifies `/auth/v1/user`; service credentials are never in browser HTML/JS. All new SQL helpers have empty search_path and explicit execute privileges. New sidecar actual reports are attributed, immutable in the audit, idempotent by request UUID and do not book counts. Runs are immutable. Publication checks the complete source fingerprint, age, actor authorization, result identities and monotonically newer calculation time before atomically inserting cache/announcements. Failed publication rolls back all those writes. The fingerprint is a change token, not an authorization signature.

Source changes invalidate cached results on the next scoped read and queue recalculation; expired cache is also queued. `production-forecast-worker` processes at most ten departments per call. It is **not deployed or scheduled**. When separately approved, invoke it with the platform's required Authorization and an independent `x-forecast-worker-secret`; configure exact UI allowed origins and server credentials. User-triggered recalculation/reporting uses `production-forecast`. No workflow invokes or deploys either endpoint. Worker environment flag is off when absent; a consumer must be configured and verified before any activation. The UI polls scoped source/cache state every 30 seconds while enabled, and invalidates an expired visible forecast and refreshes the readiness display. Transport errors show unknown and retain the ability to retry.

The sole replacement of #9's material function adds freshness validation for generated forecast sources. Confirmed `started_here` and complete received quantity stay first in precedence. Manually verified existing external arrival sources (no forecast run ID) keep #9 semantics. No generated forecast writes execution, handover, work-start or partial quantities. Source fingerprints exclude derived display version numbers so reading an announcement cannot invalidate its own forecast. A later/failed/duplicate result cannot overwrite physical states or roll a cache backwards.
