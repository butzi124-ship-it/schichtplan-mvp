## Isolation and actual execution evidence

Initial CI attempts confirmed a healthy container-local PostgreSQL but runner-to-published-port ECONNREFUSED. The client was moved inside the isolated network rather than relaxing network isolation. Those attempts executed no migrations and are not passing integration runs.

The Work environment has no Docker, Podman, PostgreSQL, Supabase CLI or Docker socket. The new `Isolated Database Acceptance` workflow runs real version-pinned PostgreSQL/Supabase GoTrue/PostgREST/Edge Runtime containers on an ephemeral GitHub runner. No hosted project, Supabase branch, account secrets, production DB URL or paid Supabase resource is used. Images are pulled before creating an **internal** Docker network. No ports are published. The Node test client executes in an internal gateway/test container; fixed loopback TCP proxies reach only the named test services. Actual image digests, internal-network verification and test results are artifacts. Test passwords/JWT keys are random per run, kept outside the repo in a mode-0600 file and destroyed with containers/volumes/network. No credentials or auth/health records are uploaded. The target guard rejects any non-loopback connection, wrong DB/port or missing random instance sentinel. Production project `itntnpzqzyjfdnjdshvm` is never a target. Neither the live application nor production/personnel data is read.

The production Edge entry files are bundled with the exact pinned Temporal dependency, then run in the real Edge Runtime. A small internal-only gateway forwards only Auth and REST to the test services. GoTrue generates actual login JWTs; PostgREST verifies them and switches actual database roles. Tests also use independently connected native PostgreSQL clients for concurrency; no PGlite/global-session role simulation is used in this job. Both forecast and worker are enabled/invoked **only inside these artificial test containers**. No production worker is deployed, scheduled or started. Existing e2e/Quality Gate dependencies and deployment restrictions remain unchanged; the new integration status is separately visible and must be considered explicitly during review.

## Fidelity: a verified catalog mirror is not a full restore

`docs/qa/schema-inventory.json`, captured 2026-11-05, explicitly says `restorable:false`. Its 31 tables, 308 column types/defaults/nullability, 134 constraints, 127 policies and 11 triggers are reconstructed and compared before applying anything. Four SQL files are then executed in the requested order, each in its own transaction: expected table counts **31→38→41→46→57**, recording SQL hashes. This proves execution only against the **structural catalog mirror**, not authoritative production compatibility.

Missing: original function definitions/signatures/owners/ACLs (the read-only report counted five public SECURITY DEFINER functions, but did not identify all); original `set_updated_at` body; complete table/sequence/default grants and standalone indexes; current authoritative schema-only dump. Three policy helpers and the timestamp trigger are **explicit test substitutes**, not recovered production definitions. Other than the confirmed A/B grants, table ACLs are declared fixture assumptions. Auth uid/jwt accessors model the actual Supabase request-claims contract, while authentication/JWT validation itself is real GoTrue/PostgREST. These gaps appear in the result artifact and prevent a claim of full production-schema acceptance even if all tests pass.

Embedded PGlite was used only as a preliminary generator/syntax check; its output is not counted as native integration evidence. A real-run startup failure is BLOCKED/NOT TESTED and never falls back to embedded/mock success.

## Coverage and baseline security meaning

Real integration cases cover GoTrue signup/login, JWT tampering, all 26 new tables' RLS/ACL restrictions, cross-department and user-metadata spoof denials, released revisions and immutable three-OP snapshots, two independent BAs, duplicate BA races on separate PostgreSQL connections, rollback, concurrent idempotent full physical handover, no partial/predicted release, the actual forecast Edge/worker APIs, sickness/vacation/shift cancellation and unchanged legacy counters/scrap/checklists.

The baseline deliberately reproduces findings A/B using real anonymous and user HTTP/JWT access: ten RLS-disabled tables with anon DML grants, and foreign employee-role editing under permissive policies. **A passing vulnerability-reproduction test does not mean the vulnerability is fixed.** Artifact state remains `CRITICAL_BASELINE_FINDINGS_REPRODUCED_NOT_FIXED`. Corrections belong in a separate Draft PR with a separate access matrix, tests and rollback review. Unknown original definer bodies and indexes must not be invented, indiscriminately revoked or dropped.

## Controlled backup / rollback / eventual activation plan (not executed in production)

1. Obtain separately authorized authoritative **schema-only** dump, full function definitions/owners/execute ACLs, role/default grants, indexes and policy metadata. No personal or manufacturing rows in test fixtures. Compare capture timestamp/catalog digest with a reviewed baseline. Keep credentials outside artifacts.
2. Review a role/task matrix for admin, department responsibility, employees and scanner, including medical/absence privacy, replacements, tool journaling and direct production-count API behavior. Independently provision trusted privileges; never bootstrap from user-editable metadata or currently mutable employee roles.
3. Restore the authoritative schema to a new isolated stack. Repeat native SQL/JWT/RLS/parallel/Edge tests and all existing regression jobs. Reconcile any substitute-function or ACL difference; all such differences block production acceptance. Add load, real Realtime and session-revocation tests if those paths are to be activated. The catalog mirror cannot substitute for this step.
4. Before any separately approved production change, verify an encrypted backup/PITR checkpoint and perform a restore drill in a separate environment. Capture schema/ACL/function hashes and module flags; confirm recovery owner, maintenance window and rollback criteria. Never test rollback on production.
5. Apply reviewed security changes and feature migrations in independently approved, controlled transactions, with lock/statement timeouts. #7→#8→#9→#10 only after prerequisite verification. Failures roll back the whole failed transaction; do not continue blindly. Keep all four browser flags, server flags, settings and workers off.
6. Rollback prefers transaction abort before commit or reverting policies/functions using an exact reviewed pre-change schema/ACL backup. After any accepted real writes, **do not drop snapshot/audit tables or overwrite counts**; disable flags/workers and preserve data. Restore/PITR is an explicitly authorized incident decision with a tested loss window, not an automatic script.
7. Only after separate owner approval, staged synthetic/canary verification and monitored permission/latency checks activate one module at a time. No CLI link, hosted migration, deployment, merge, feature activation or production worker is part of this PR.
